## 쟁점 1 — 문자 영역 순서 바꾸기 (A-7)

- **내 주장**: 자주 사용하는 문자 영역을 위로 옮길 수 있으면 탐색을 빠르게 하고 사용자의 통제권을 높일 수 있다.
- **반론 (AI)**: 메뉴가 열 때마다 달라지면 위치를 다시 찾아야 하고, 다섯 개 카드의 순서를 편집하는 UI가 단순한 허브를 복잡하게 만들 수 있다(P01, P04, P08). 드래그 조작과 복구 수단도 필요하다.
- **재반론·수정**: 고정 순서의 예측 가능성은 장점이지만, 사용자는 개인별 순서 변경을 원했다. 카드 전체를 드래그하게 하지 않고 우측 `=` 핸들만 재배치를 시작하게 하며, 카드 본문 탭은 학습 목록 진입으로 유지했다.
- **결론**: **수정**. 사용자 순서 변경은 허용하되 조작 영역을 핸들로 한정한다. 순서는 현재 실행 세션에서만 유지한다.
- **근거**: P03 사용자 통제, P07 효율성, P08 간결성. 코드 근거: `lib/screens/a_list_screen.dart`의 `_HubListViewState`, `ReorderableListView.builder`, `ReorderableDragStartListener`.
- **전·후 자료**: 초기안은 고정 순서 허브, 변경안은 핸들 드래그 허브다.
- **증거**: `docs/prompt-log.md`의 “메인 화면 항목 순서를 사용자가 직접 바꿀지” 및 “메인 허브의 문자 영역 순서를 사용자가 변경” 항목. R19의 주제별 단어 분류 요청은 개인화 탐색에 대한 간접 근거일 뿐, 카드 재정렬을 직접 요청한 리뷰는 아니다.

## 쟁점 2 — 문자 예시와 학습 진척도 (A-7)

- **내 주장**: 허브 카드 아래의 `ㄱㄴㄷ…` 같은 예시보다 학습한 글자 수를 표시하는 편이 현재 진행 정도를 파악하는 데 유용하다.
- **반론 (AI)**: 예시 글자는 영역의 문자 체계를 재인하게 돕는다(P02, P06). 숫자만으로 바꾸면 무엇을 학습하는 영역인지 덜 분명해질 수 있고, 퍼센트는 분모가 무엇인지 알려 주지 않을 수 있다.
- **재반론·수정**: 요청한 것은 퍼센트가 아니라 실제 수 `학습한 글자 / 전체 글자`다. 아이콘과 영역 이름은 유지하고, 진척도는 보조 정보로 표시한다. 즐겨찾기는 학습 진척도가 아니라 `n개 단어`로 표시한다.
- **결론**: **수정**. 예시 문자열을 진척도 텍스트로 교체하고, 즐겨찾기 카드는 개수만 표시한다. 진행 바는 두지 않는다.
- **근거**: P01 상태 가시성, P06 재인, P08 미니멀. 유사앱 캡처에는 신규·복습·완료 요약이 보이고, R08(2026-10-11 · ★3)은 학습 후 상태가 원하는 기억 단계로 이동하지 않는 오류를 보고했다. 이를 참고해 상태가 보이도록 하되, 앱은 사용자가 요청한 영역별 학습 수/전체 수로 단순화했다. 코드 근거: `lib/screens/a_list_screen.dart`의 `progressByCategory`와 `_HubListViewState`.
- **전·후 자료**: 초기안은 문자 예시 카드, 변경안은 학습 수/전체 수 표시 카드다.
- **증거**: `docs/prompt-log.md`의 “메인 허브의 문자 영역 순서를 사용자가 변경하고 각 영역의 학습 진척도를 표시” 항목.

## 쟁점 3 — 획수 태그를 드롭다운으로 통합 (A-9)

- **내 주장**: 검색 아래 획수 칩이 너무 많으므로 드롭다운으로 묶어 화면을 정돈한다.
- **반론 (AI)**: 드롭다운은 선택지가 닫힌 상태에서 보이지 않아 현재 필터 상태를 놓치게 할 수 있다(P01). 너무 많은 선택을 숨기면 탐색 효율도 떨어질 수 있다(P07).
- **재반론·수정**: 획수만 하나의 선택 메뉴로 묶되 일반 태그의 흐름 안에 두고, 가장 오른쪽 태그로 배치한다. 화면 바깥 끝에 고정하지 않고 다른 태그와 높이·테두리 톤을 맞춘다.
- **결론**: **수정**. 일반 태그 칩은 유지하고 획수 필터만 태그 행 마지막 드롭다운으로 제공한다. `전체 획수`로 해제할 수 있게 한다.
- **근거**: P01 상태 가시성, P05 오류 예방, P07 효율성, P08 미니멀. 태그 행의 정보량을 줄이고 필터 상태를 알아보기 쉽게 하려는 설계 판단으로, 획수만 드롭다운에 통합했다. 코드 근거: `lib/screens/a_list_screen.dart`의 `strokeTags`, `_selectedStrokeTag`, `DropdownButton`.
- **전·후 자료**: 초기안은 획수별 칩이 나열된 태그 행, 변경안은 태그 행 마지막의 획수 드롭다운이다.
- **증거**: `docs/prompt-log.md`의 “획수 태그를 드롭다운 메뉴로 바꿀지” 및 “획수 드롭다운의 위치와 시각 스타일을 수정” 항목.

## 쟁점 4 — 학습 완료를 되돌릴 수 있게 하기 (B-5)

- **내 주장**: 사용자는 글자를 잊거나 상태를 잘못 표시할 수 있으므로 학습 완료를 취소하고 학습 중 또는 미학습으로 되돌릴 수 있어야 한다.
- **반론 (AI)**: 완료 상태를 여러 버튼으로 바꾸면 조작 실수와 상태 혼란이 생길 수 있다(P01, P08). 완료를 되돌릴 때 획득 캐릭터가 사라지는지도 불명확하면 보관함 신뢰를 해칠 수 있다(P09).
- **재반론·수정**: 상태 복구는 필요하되 캐릭터 보유와 학습 진행도는 분리한다. 완료 상태 버튼을 다시 누르면 학습 중으로 바꾸고, 별도의 `미완료로 되돌리기` 버튼으로 미학습 상태를 선택하게 한다. 이미 획득한 캐릭터는 학습 상태를 되돌려도 보관함에 남긴다.
- **결론**: **수정**. 완료·학습 중·미학습으로 복구 경로를 제공하고 상태별 문구를 명시한다.
- **근거**: P01 상태 가시성, P03 통제와 자유, P04 일관성, P07 효율성, P09 복구. 첨부 캡처의 필기 비교 화면에는 교정 결과 뒤에 `고쳐 쓰기` 행동이 있다. 이를 수정 기회의 근거로 참고하되, 점수·유사도 계산은 구현하지 않고 학습 상태 복구로 제공한다. 코드 근거: `lib/main.dart`의 `_changeLearningStatus`, `lib/screens/b_detail_screen.dart`의 `_setStatus`와 상태 버튼.
- **전·후 자료**: 초기안은 완료 이후 복구 동작이 없는 화면, 변경안은 완료 토글과 미완료 버튼이 있는 화면이다.
- **증거**: R08(2026-10-11 · ★3 · Google Play)은 완료 버튼을 눌러도 장기기억으로 이동하지 않는 문제를 보고했다. 이는 우리 앱의 되돌리기 요구와 동일한 문제는 아니지만, 학습 상태가 의도와 다르게 보이면 사용자가 상태를 신뢰하기 어렵다는 근거다. 구현은 `test/widget_test.dart`의 상태 복구 테스트로 확인했다.

## 쟁점 5 — 새 캐릭터 알림 (A-1, D-2)

- **내 주장**: 새로 획득한 캐릭터를 놓치지 않도록 보관함 아이콘 숫자와 카드 표시를 두고 싶다.
- **반론 (AI)**: 보유 수와 미확인 수가 혼동될 수 있고, 보관함을 열기만 해도 모든 새 알림이 사라지면 개별 캐릭터의 확인 상태를 놓칠 수 있다(P01, P09).
- **재반론·수정**: 숫자는 미확인 캐릭터 수만 나타내고, 보관함의 미확인 카드 우상단에 빨간 점을 표시한다. 보관함 진입만으로 전체를 읽음 처리하지 않고, 실제 카드를 누른 캐릭터만 읽음 처리한다.
- **결론**: **수정**. 획득·조회 상태를 캐릭터별로 관리한다. 이 상태는 프로토타입 규칙에 따라 영구 저장하지 않는다.
- **근거**: P01 상태 가시성, P03 사용자 통제, P09 오류 인식·복구. 코드 근거: `lib/main.dart`의 `_unviewedCharacterGlyphs`, `lib/screens/a_list_screen.dart`의 보관함 `Badge`, `lib/screens/d_collection_screen.dart`의 카드 표시 및 `onCharacterViewed`.
- **전·후 자료**: 초기안은 보유 캐릭터 수 배지, 변경안은 미확인 수와 카드별 빨간 점 표시다.
- **증거**: R18(2026-05-28 · ★5 · Google Play)은 한자 즐겨찾기와 복습 기능을 요청했다. 이 요구를 재방문 설계의 근거로 삼고, 캐릭터 보관함은 Charverse의 학습 보상 흐름에 연결했다. `docs/prompt-log.md`의 배지 변경 기록과 미확인 캐릭터 위젯 테스트를 함께 참조한다.

## 쟁점 6 — 캐릭터 보관함을 화면 D로 명시하기

- **내 주장**: 캐릭터가 수집의 핵심 보상이라면 메인 허브에서 보관함으로 바로 진입할 수 있어야 한다.
- **반론 (AI)**: 화면 D를 추가할 때에는 비즈니스 명칭과 화면 전환 흐름을 기획 문서에 함께 반영해야 한다.
- **재반론·수정**: 기능을 없애기보다 디자인 가이드에 화면 D의 비즈니스 명칭, 진입 방식, 위젯 요소, 상태를 추가해 구현과 기획을 일치시킨다. 별도 전환은 허용된 쌓기(push) 방식으로 제한한다.
- **결론**: **수정**. 화면 D를 디자인 가이드에 명시하고, A의 보관함 아이콘에서 push로 진입하는 구조를 기록한다.
- **근거**: P03 복귀 경로, P06 캐릭터와 글자 재인, P07 수집 접근 효율, P08 정돈된 그리드. 유사앱 캡처의 학습 목표/전략 선택 화면은 별도 흐름이지만 이를 그대로 추가하지 않고, 기존 허브에서 보관함으로 이동하도록 제한했다. 코드 근거: `lib/screens/d_collection_screen.dart`의 `CollectionScreen`, `GridView.builder`, `FilledButton`.
- **전·후 자료**: 초기안은 A–C 흐름, 변경안은 화면 D를 포함한 A–D 흐름이다.
- **증거**: R18(2026-05-28 · ★5 · Google Play)의 “한자는 별도의 즐겨찾기나 복습 기능이 없는 것 같네요” 의견을 바탕으로 보관·재방문 흐름을 설계했다. 캐릭터 보관함은 Charverse의 학습 보상 기획과 연결했으며, 관련 설계 기록은 `docs/prompt-log.md`에 정리했다.
